## Conception proposée (non validée, à reprendre)

- **Qui peut demander** : le pont ACP déclare à la création de session qu'il sait répondre (champ dans la config de `create`, par exemple `yaPermissionAsker: true`). Le worker passe alors un demandeur à `create_session_with` ; sans ce champ (TUI avant la PR 3), refus à la création comme aujourd'hui (message D6). Limite à noter : un TUI qui s'attache à une session créée par ACP voit les demandes sans pouvoir y répondre.
- **Demandeur du worker** (module du fork dans `pa-daemon`) : table `requestId → oneshot` ; `ask` émet un événement de session `ya_permission_request { requestId, toolCallId, toolName, args }` par l'`EventPump`, attend la réponse ou l'`AbortSignal` (→ `Cancelled`), puis émet `ya_permission_resolved { requestId, outcome }` pour fermer la demande chez les autres clients.
- **Réponse client → worker** : commande `ya_permission_response { requestId, outcome: "allow" | "deny" }` (les points d'insertion du § 2) ; issue inconnue = refus.
- **Pont ACP** : sur `ya_permission_request`, requête JSON-RPC sortante `session/request_permission` (`sessionId`, `toolCall` avec `toolCallId` et `status: "pending"`, `options` : `{optionId: "allow-once", kind: "allow_once"}`, `{optionId: "reject-once", kind: "reject_once"}`) avec un id et une table d'attente ; `parse_line` accepte les réponses (nouvelle variante d'`Incoming`, test `jsonrpc.rs:124-125` à adapter) ; réponse `selected allow-once` → `allow`, autre chose → `deny`, `cancelled` → `deny` (le tour est déjà en annulation). Après un accord : `tool_call_update` en `in_progress`.
- **Journal** : voir le constat § 5.
- **Sélecteur `permissions` dans `session/set_config_option`** : prévu au plan du ticket pour la PR 2 (section 7), **non demandé explicitement** dans la demande du 20/11 ; à confirmer avec Yusuf (il demande que le gate existe aussi en « auto » quand un demandeur est présent, avec un mode modifiable à chaud).
