## Biais prévus au plan

- **Schéma réduit.** `tty`, `shell` et `login` ont été retirés, ainsi que les paramètres de sandbox et d'approbation (`crates/pa-core/src/tools/ya_exec.rs:8-11`).
  - La description, reprise mot pour mot de Codex, annonce pourtant un PTY : « Runs a command in a PTY, returning output or a session ID for ongoing interaction. » (`ya_exec.rs:53-54`).
  - Le modèle demande `yield_time_ms` à 1000 dans 99 appels `exec_command` sur 115. Le processus tourne encore au retour dans 64 cas.
  - Une sonde de `write_stdin` à `chars` vide attend au moins 5 s (`ya_exec.rs:63`, `:279-280`, comme Codex d'après `ya_exec.rs:13-20`).
  - D'où 103 `write_stdin`, tous à `yield_time_ms` 1000. C'est un coût en tours pour B qui vient du contrat d'interface plus que du shell. Ce point est noté pour une reprise éventuelle de la variante (`docs/tickets/10-ya03-shell-natif.md`).
- **Règle de prompt.** La règle « pas de boucles shell ni de heredocs » est remplacée dans B (`crates/pa-core/src/prompts/ya_tools_prompt.rs:48`, `:136`). B n'a écrit aucun heredoc ni aucune boucle shell. Le retrait n'a donc pas d'effet visible ici, mais il reste confondu avec le tool.
- **Unités.** Le tool natif compte en octets, `python_repl` en caractères.
  - Les sorties shell de B font 250 183 octets pour 240 234 caractères (+4,1 %), à cause des ✔ et ▶ des reporters Node.
  - Les 17 sorties shell tronquées de B ont toutes un `max_output_tokens` demandé par le modèle, entre 500 et 3000 (2 000 à 12 000 octets), bien sous le plafond de session. La troncature vient donc du budget demandé, pas de l'unité de comptage.
- **Format.** Le tool de la variante suit `exec_command` de Codex (en-tête `Wall time` / `Process exited with code` / `Original token count` / `Output:`), sans format maison. Le biais « format maison » du plan ne s'applique pas.

## Anomalies

- **Aucun bras ne sort de [0,5 ; 2] fois la médiane** du coût théorique des 6 bras de sa tâche. Les plus forts écarts :
  - `node-testsprite-356`, passe 2, bras B : ×1,56 ;
  - `py-shortuuid-118`, passe 3, bras B : ×1,53.
- **`node-testsprite-356`, passe 2, bras B** (218 s de tâche contre 97 à 130 s pour les 5 autres bras, 27 tours, 0,0857 $) :
  - c'est le seul bras de la tâche qui lance la suite complète (`npm run lint && npm test`). Les autres ne lancent que les tests ciblés ;
  - il la sonde ensuite 16 fois par `write_stdin`, toutes les 5 s environ, pendant 2 min ;
  - c'est un choix du modèle, amplifié par la sonde à 5 s minimum, pas une panne. La tâche est résolue.
- **Deux résolutions inhabituelles, deux vrais correctifs.** Dans les deux A/B, les 22 bras en échec sur les deux tâches non stables échouent chacun sur un seul test, qui passait déjà avant le correctif (`pass_to_pass`). Dans chacun de ces 22 bras, l'agent a réécrit ou retiré le test existant qui l'exprime. Les deux bras résolus l'ont laissé intact (détail au ticket 09, points ouverts) :
  - **`node-filesize-376`, passe 2, bras A.** Le test qui échoue ailleurs est `should retain zero precision when a locale is requested` (`bench/smoke/tasks/node-filesize-376/task.toml:155`). Les autres bras réécrivent l'assertion visible `filesize(0, { locale: "de-DE", precision: 3 })` de `"0.00 B"` en `"0,00 B"`. Le bras résolu garde le comportement existant pour zéro (« J'ai conservé le comportement existant pour une entrée nulle avec précision »).
  - **`node-little-coder-102`, passe 1, bras B.** Le test qui échoue ailleurs est `does not extract from nested-object bare JSON` (`bench/smoke/tasks/node-little-coder-102/task.toml:59`). Les autres bras étendent `firstBalancedObject` à l'extraction du JSON nu (`bareRe`) et réécrivent ou retirent ce test. Le bras résolu limite le correctif à `repairJson`, comme le demande le point 3 de l'énoncé.
  - Ces deux tâches sont instables parce que l'énoncé est ambigu et que l'agent comble l'ambiguïté en modifiant un test existant. Le tool shell n'y est pour rien. Les énoncés restent tels quels.
